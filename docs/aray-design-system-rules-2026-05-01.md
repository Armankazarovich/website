# ARAY Design System Rules — 2026-05-01

Этот документ фиксирует общий визуальный закон ARAY Production для админки, ПилоРус, будущих клиентских сайтов, попапов, мобильных меню, конструктора, виджетов и внутренних инструментов.

## Главная идея

Каждый отступ, шрифт, цвет, иконка и карточка должны быть осознанными. Интерфейс не должен выглядеть как набор случайных блоков: одна выбранная атмосфера управляет акцентом, карточками, иконками, прогрессом, hover/focus состояниями и общим настроением.

Цель: пользователь выбирает стиль один раз и везде чувствует тот же характер системы.

## Цвет и атмосфера

- Палитра — это не просто цвет кнопки, а настроение интерфейса.
- Основной акцент берется из выбранной палитры через `hsl(var(--primary))`.
- Базовые поверхности должны оставаться спокойными: `background`, `card`, `popover`, `border`, `muted`.
- Нельзя превращать интерфейс в радугу. Разные декоративные цвета у иконок, карточек и быстрых действий запрещены.
- Семантические цвета разрешены только по смыслу:
  - warning — реально требует внимания;
  - success — реально успешно/готово;
  - danger — ошибка, риск, удаление, критичный статус;
  - info — системная подсказка, если она не конкурирует с основным акцентом.
- Если цвет ничего не сообщает, он должен быть палитро-зависимым, а не отдельным.

## Иконки

По умолчанию иконки используют общий тон выбранной атмосферы:

- `ARAY_ICON_TONE` — основной палитро-зависимый тон.
- `ARAY_ICON_TONE_MUTED` — спокойная служебная иконка.
- `ARAY_ICON_TONE_WARNING` — только реальное внимание.
- `ARAY_ICON_TONE_SUCCESS` — только реальный успех.
- `ARAY_ICON_TONE_DANGER` — только реальный риск/ошибка.

Источник токенов: `lib/aray-design-tokens.ts`.

Правило: если в новом разделе нужна иконка, сначала использовать эти токены. Свой цвет добавлять только если это новый подтвержденный семантический статус.

## Палитры

Палитры строятся как “8 характеров + фирменный ARAY”.

- 8 характеров дают пользователю разные настроения интерфейса.
- 9-я палитра — `ARAY`, фирменная: глубокий графитово-синий фундамент, золотой акцент, ощущение воды, золота и интеллекта.
- Внутренний id `sber` пока сохраняется ради совместимости старых настроек, но пользователь видит название `ARAY`.

## Фото-фоны

- Фото-атмосферы — фича только единой админки ARAY.
- Клиентские публичные сайты не используют эти админские фоны.
- Для клиентских сайтов визуалы подбираются или генерируются под конкретную сферу бизнеса.
- Часто лучший фон клиентского сайта — чистый, без лишней фотографии.
- Живой источник обновляемых фото для админки: `D:\ARAY PRODUCTION\ФОН ДЛЯ ПЛАТФОРМЫ`.
- Связка палитра -> админское фото хранится в `lib/admin-atmospheres.ts`.

## Карточки выбора оформления

- Маленькие декоративные кружки в карточках палитр не использовать: они могут выглядеть как сломанные иконки или ошибка загрузки.
- Карточка должна показывать реальное ощущение атмосферы: фото-превью, мягкий overlay, нижняя двухцветная линия `sidebar + accent`, понятная галочка выбранного состояния.
- Выбранная карточка подсвечивается рамкой и спокойной тенью от текущего `primary`.
- Hover должен помогать выбрать, но не шуметь.

## Отступы и плотность

- Рабочие панели должны быть плотными, но дышащими.
- Карточки в админке держать в едином ритме: одинаковые скругления, похожая высота, одинаковая логика внутренних отступов.
- Не вкладывать визуальные карточки в карточки без сильной причины.
- Текст внутри компактных панелей не должен быть hero-размера.
- На desktop, tablet и mobile элементы не должны прыгать, перекрываться или менять размер из-за hover/label/icon.

## Адаптивность и touch

- Все страницы проектировать сразу для mobile, tablet, desktop, больших сенсорных мониторов, касс, телевизоров и PWA.
- Интерфейс должен быть резиновым: без фиксированных ширин, которые ломают экран; использовать `max-width`, responsive grid, переносы и scroll-зоны.
- Основные touch-цели держать не меньше 44px по высоте/ширине.
- Icon button должен иметь понятный hit area, даже если сама иконка маленькая.
- Панели настроек и попапы обязаны иметь внутренний scroll, чтобы на маленьком экране кнопки не уходили за пределы viewport.
- Hover-эффекты не должны быть единственным способом понять состояние: selected, active, disabled и focus должны быть видны и на touch.
- На больших мониторах не растягивать текст и карточки до бесконечности; контент должен сохранять читабельную ширину и ритм.
- Для фокуса использовать общий токен `ARAY_FOCUS_RING`, для touch-целей — `ARAY_TOUCH_TARGET`.

## Движение и скорость

- Анимация нужна для ощущения живой системы, но не должна мешать работе.
- Фото-фоны можно плавно менять с Ken Burns/slide-fade, но без постоянной тяжелой перерисовки интерфейса.
- При смене палитры не делать лишних запросов за фото, если фото уже известны.
- Первые фото надо подгружать заранее, чтобы переключение атмосферы ощущалось легким.

## Hover, блеск и живой отклик

- Hover-эффекты — часть фирменного почерка ARAY, но они должны быть спокойными, дорогими и функциональными.
- Базовый интерактивный слой: `admin-liquid-surface` + `admin-liquid-interactive`.
- В коде для переиспользования держать токены: `ARAY_LIQUID_SURFACE`, `ARAY_LIQUID_INTERACTIVE`, `ARAY_SHIMMER_TRACE`, `ARAY_ICON_HOVER_LIFT`.
- Основной hover: мягкий подъем до 1px, легкая рамка `primary`, спокойная тень от текущей палитры, едва заметный orbit/glass shine по контуру.
- Иконка внутри карточки может чуть увеличиваться через `group-hover:scale-110`, но не должна менять цвет на случайный.
- `shimmer-trace` использовать точечно: для важных карточек, CTA, премиальных элементов и демонстрационных блоков. Не ставить на каждый мелкий список.
- На touch-устройствах hover не должен быть обязательным для понимания; active/focus/selected состояния обязаны работать отдельно.
- Уважать `prefers-reduced-motion`: блеск, орбита и подъем должны отключаться или становиться статичными.
- Запрещены дешевые эффекты: кислотный неон, постоянное свечение всех карточек, сильный scale, прыгающие layout-эффекты, разноцветный glow без смысла.
- Эффект должен отвечать на действие пользователя, а не спорить с контентом.

## PWA, APK и идентичность приложений

- Админка ARAY — отдельное PWA-приложение со своим названием, иконками, favicon, theme-color и manifest.
- Каждый клиентский публичный сайт — свое PWA-приложение с логотипом, favicon и иконками клиента, не с нашими знаками.
- Ролевые приложения можно выделять отдельно: владелец, менеджер, курьер, официант, склад, касса, водитель, исполнитель, партнер.
- У каждой роли может быть свой `name`, `short_name`, `start_url`, `scope`, набор прав, стартовый экран, push-уведомления и быстрые действия.
- APK/standalone-упаковки должны наследовать тот же manifest и бренд-контекст, чтобы приложение выглядело родным на телефоне, планшете, кассе, телевизоре, touch-мониторе и Android-магнитоле.
- Наши логотипы ставятся на наши продукты: ARAY admin, ARAY Production, биржа, конструктор, внутренние сервисы. На клиентских сайтах главный знак — знак клиента.
- ARAY Assistant может работать как голосовой слой поверх ролей: рассказать выручку, статус заказов, наличие товара, подсказать действие.
- Для автомобиля и магнитолы делать отдельный безопасный driver/head-unit режим: голос первым, крупные элементы, минимум касаний, без сложных таблиц и без сценариев, отвлекающих водителя в движении.

## Уведомления, роли и доступы

- Роли, права и уведомления должны проектироваться как единая система, а не набор случайных условий внутри страниц.
- У каждой роли свой сценарий: владелец, менеджер, курьер, официант, склад, касса, бухгалтер, маркетолог, исполнитель, партнер, клиент.
- Интерфейс должен показывать человеку только те действия, данные и уведомления, которые ему реально нужны.
- Уведомления делятся по важности: критично, требует действия, информационно, тихая история.
- Цвет уведомления должен быть семантическим: danger/warning/success/info только по реальному смыслу.
- Каналы уведомлений выбирать умно: in-app, push/PWA, email, Telegram, SMS/звонок, рабочий чат, voice через ARAY.
- Для touch/полевых ролей уведомления должны быть короткими, крупными и action-first.
- Для владельца уведомления должны показывать состояние бизнеса, деньги, риски, рост и рекомендации, а не шум.
- Нужны quiet hours, группировка повторов, журнал доставки и объяснение “почему я это получил”.

## Применение ко всей экосистеме

Эти правила действуют для:

- админки ARAY / ПилоРус;
- будущего конструктора сайтов;
- клиентских кабинетов;
- публичных клиентских сайтов;
- попапов, модалок, мобильных меню;
- ARAY Assistant и чата;
- CRM/ERP, финансы, кошелек, маркетинг, интеграции.

Если новый раздел выглядит “сам по себе”, значит он еще не встроен в систему.

## Практическое правило для разработки

Перед добавлением нового блока проверять:

1. Он берет цвет из текущей палитры?
2. Его иконки используют ARAY токены, а не случайные цвета?
3. Семантический цвет действительно несет смысл?
4. Отступы и размер текста совпадают с соседними блоками?
5. На mobile/tablet/desktop все остается читаемым?
6. Пользователь поймет, что это элемент системы ARAY, даже если убрать логотип?
