# Admin Foundation Audit — ночная карта фундамента

Дата: 2026-04-30

## Цель

Подготовить админку PiloRus/ARAY к стабильной работе как будущего ядра платформы для разных бизнесов.

Эта карта нужна, чтобы не чинить хаотично по одному скриншоту, а идти по фундаменту:

- навигация;
- роли;
- медиа;
- действия в хедере;
- мобильная/PWA-логика;
- дизайн-система;
- будущая повторяемость для Zaidr, тары/коробок и других ниш.

## Что уже есть хорошего

В админке уже собран сильный новый каркас:

- `AdminShell` — общая оболочка админки;
- `AdminNavRail` — боковой rail с группами и раскрывающейся панелью;
- `AdminPageActionsProvider` — единая система действий страницы в хедере;
- `AdminSearchPanel` — отдельный поиск;
- `AdminAtmosphere` — локальные WebP-фоны и режимы clean/photo;
- `ArayControlCenter` — переключение темы, палитры и фона;
- `AdminDeferredClientTools` — отложенная загрузка тяжелых клиентских инструментов;
- `AccessGuard` — клиентская защита разделов;
- `media-permissions` — отдельные права на медиабиблиотеку;
- `UI_LAYERS` — общий z-index-контракт для слоев.

Это хорошая база. Ее нужно не ломать, а привести к единому стандарту.

## Главные риски

### 1. Дубли источников правды

Сейчас данные о разделах и правах живут в нескольких местах:

- `components/admin/admin-nav.tsx` — навигация, роли, группы, иконки;
- `components/admin/admin-shell.tsx` — заголовки страниц и fallback actions;
- `components/admin/admin-nav-rail.tsx` — подписи/сабтайтлы групп;
- `components/admin/admin-menu-popup.tsx` — отдельные highlights и quick actions;
- `lib/permissions.ts` — доступ к разделам;
- `lib/media-permissions.ts` — права на медиа.

Для PiloRus это еще терпимо, но для ARAY Production это опасно. При новой роли или новом разделе легко обновить одно место и забыть другое.

### 2. Навигация должна быть touch-first

Rail уже умеет pinned group по клику — это правильно для сенсорных мониторов и телевизоров.

Нужно закрепить правило:

- hover — только улучшение;
- click/tap — основной стабильный сценарий;
- Escape/клик снаружи закрывает;
- смена маршрута закрывает;
- mobile/tablet имеют отдельную устойчивую механику.

### 3. Старые дизайн-слои еще встречаются

В комментариях и отдельных компонентах видны следы старых подходов:

- calm UI магазина;
- старый search modal;
- старые sidebar/neural/video идеи;
- отдельный `admin-search.tsx`;
- локальные стили в компонентах.

Не все из этого плохо, но нужно постепенно убрать дубли и оставить один ARAY admin kit.

### 4. Медиабиблиотека пока не выглядит как единая база платформы

API `/api/admin/media` сканирует папки и строит usage map по продуктам/категориям.

Плюсы:

- есть роли;
- есть защита удаления используемых фото;
- есть ALT;
- upload конвертирует изображения в WebP через sharp;
- есть проверка MIME/ext/magic number.

Риски:

- медиа живет в файловой структуре, а не в полноценной таблице assets;
- нет единого tenant/media registry;
- не все источники использования могут быть учтены;
- видео разрешены, но пользователь хочет снизить нагрузку и чаще использовать фото + parallax/zoom;
- нужна единая логика “медиабиблиотека проекта” для всех разделов и будущих клиентов.

### 5. Products имеет важный missing route

В хедере есть fallback action `/admin/products/new`, но в дереве файлов нет `app/admin/products/new/page.tsx`.

Это значит: кнопка “Новый товар” потенциально ведет на несуществующую страницу. Нужно либо:

- сделать страницу создания товара;
- либо временно заменить действие на существующий сценарий;
- либо вести в каталог с понятным drawer/modal, если он уже реализован.

Это важный баг-кандидат.

### 6. PWA и safe-area уже частично учтены, но нужен аудит

Есть:

- `admin-manifest.json`;
- `appleWebApp` metadata;
- `theme-chrome-sync`;
- `AdminPwaInstallBridge`;
- safe-area в mobile nav, Aray chat/dock, admin shell.

Нужно позже проверить:

- статус-бар iPhone;
- theme-color при смене темы/палитры;
- install prompt на desktop/mobile;
- поведение в standalone PWA;
- push/banner уведомления.

## Рекомендуемый архитектурный порядок

### Шаг 1. Единый Admin Registry

Создать единый источник правды для разделов:

- id;
- href;
- title;
- subtitle;
- icon;
- group;
- roles;
- section permission key;
- quick actions;
- search metadata;
- mobile visibility;
- ARAY intent.

После этого из registry должны питаться:

- nav;
- rail;
- search;
- page titles;
- permissions;
- breadcrumbs/back fallback;
- quick actions;
- будущие подсказки ARAY.

### Шаг 2. Проверить critical routes

Автоматически проверить, что все href из админской навигации и header actions имеют существующие страницы или осознанно внешние ссылки.

Первый найденный кандидат: `/admin/products/new`.

### Шаг 3. Единый UI kit для админки

Зафиксировать набор:

- `AdminSurface`;
- `AdminSectionKicker`;
- `AdminActionButton`;
- `AdminDataTable`;
- `AdminSidePanel`;
- `AdminMobileSheet`;
- `AdminEmptyState`;
- `AdminConfirmDialog`;
- `AdminMediaPicker`.

Не обязательно все делать сразу. Но новые разделы должны постепенно переходить на этот kit.

### Шаг 4. Медиа как единая asset-система

Спланировать переход:

- от “сканируем папки” к `MediaAsset` registry в БД;
- хранить usage;
- роли;
- alt;
- folder/type/tags;
- tenant/project;
- generated/source/manual;
- оптимизированные варианты;
- связь с продуктами, категориями, постами, фонами, брендом.

Для PiloRus можно идти мягко, без резкой миграции.

### Шаг 5. PWA/a11y/performance audit

После стабилизации навигации и каталога проверить:

- desktop;
- iPhone/mobile;
- tablet;
- PWA standalone;
- theme-color;
- install prompt;
- safe-area;
- route transitions;
- heavy components lazy load;
- image sizes.

## Что можно делать без Армана

Без дополнительного обсуждения можно готовить:

- registry-аудит;
- проверку ссылок/маршрутов;
- поиск дублей ролей;
- документацию и чек-листы;
- безопасные refactor-only изменения;
- тесты и typecheck;
- анализ PWA/медиа/производительности;
- подготовку компонентов без смены визуальной идеи.

## Что лучше обсуждать с Арманом

Требует вкуса/бизнес-решения:

- финальный вид dashboard;
- 9 палитр и их смысл;
- фоновые фото;
- ARAY-панель;
- логика каждого раздела;
- отраслевые функции для Zaidr/тары/других ниш;
- что скрывать/показывать пользователям;
- юридические и финансовые формулировки.

## Ближайший практический план

1. Сделать автоматический аудит admin href → существующая страница.
2. Зафиксировать missing routes.
3. Исправить самый опасный route/action, если это очевидно.
4. Начать проектировать `admin-registry` как будущий единый источник правды.
5. Потом перейти к каталогу/товарам и медиабиблиотеке.
