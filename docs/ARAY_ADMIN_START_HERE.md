## Update 09.05.2026 - Section Approval Law

- Read `docs/SECTION_CHANGE_PROTOCOL.md` before changing any existing user-facing section.
- Every meaningful section edit starts with a snapshot: `npm run section:snapshot -- --file <path> --section <name> --reason <short-reason>`.
- After the edit, report what changed, where the snapshot lives, what checks passed, and wait for Arman's explicit approval.
- A section is `DRAFT` until Arman says it is accepted. Do not treat it as deploy-ready or use it as the new base for another redesign before that.
- This law was added after `/admin/promotion` lost a working page during a Yandex Direct rewrite. Do not repeat that pattern.

## Update 07.05.2026 - Module System Law

- New platform law: serious features are modules with a Module Passport, not isolated pages.
- Read `docs/aray-module-system-law-2026-05-07.md` before creating any big feature.
- Read `docs/aray-module-roadmap-2026-05-07.md` before planning ARAY, ads, SEO, import/export, marketplace analytics or module management work.
- Popup System is now a core module: all modal/drawer/sheet/picker surfaces must use the shared popup primitives and overlay guard.

## Update 08.05.2026 - Runtime Module Toggles

- `ArayModuleState` is the tenant-level runtime state for module toggles, role policy, subscription plan and connector policy.
- Module Control Center writes through `/api/admin/aray/modules`; core modules are locked, business modules can be toggled by SUPER_ADMIN.
- Terminal and Notifications now have server guards; admin navigation, mobile dock, search and ARAY context receive disabled module ids from the server.
- PWA icon/head sync must only touch ARAY-managed links (`data-aray-app-identity="true"`) so Next-managed head nodes are not removed by the client.

## Update 08.05.2026 - Light / Clear / Working Modules

- New product law: every module must be light, clear and working before it is presented as a real user section.
- First screens must speak human language, not internal API/provider language.
- Planned connectors, bank sync, transfers, points and other future capabilities stay clearly marked until real data, roles, audit and confirmations exist.
- Draft capabilities may live in passports and roadmaps, but must not look like finished working navigation.

## Быстрый handoff на 06.05.2026

Арман хочет открыть новый чат и сразу продолжить без повторного объяснения. Новый агент должен начать так:

4. Проверить `git status --short`.
5. Не откатывать чужие изменения: в проекте уже большой dirty worktree.
6. Продолжать с P0 ниже, а не начинать новый дизайн с нуля.

Текущий продуктовый фокус: ARAY как фирменная капсула, телефонный UX, умная навигация, задачи, уведомления, голос, переводчик, биржа/терминал, резиновые экраны.

Что уже принято как база:

- ARAY-орб является главным брендовым символом. Большой орб не трогать без причины; маленькие орбы держать чище и тоньше.
- ARAY-капсула не должна сама закрываться при переходах по страницам. Закрывает только пользователь.
- Быстрые действия ARAY не должны перегружать капсулу: максимум 3 умных prompt-кнопки + до 3 релевантных переходов.
- Если ARAY может открыть страницу или режим, он открывает сразу и отвечает коротко, но по-человечески: `Открыл нужный раздел. Проверь, пожалуйста.` или `Показал рядом. Проверь, пожалуйста.`. Одним холодным словом больше не отвечать.
- ARAY-навигация должна идти от единого реестра: основные разделы, служебные страницы, подключение сервисов, модули, лимиты, импорт/ремонт/настройки. Новая рабочая страница добавляется в navigation registry / route classification и сразу становится понятной ARAY, поиску и mobile.
- Внутренние переходы и попапы платформы должны идти к единой phone-like slide-анимации.
- Hover-эффект с градиентом использовать только на важных интерактивных кнопках/переходах, не на всех карточках.
- Все данные аналитики биржи, рейтинги, просмотры, спрос, остатки, история цен и отзывы должны быть честными: если нет событий, показывать `нет данных`, не выдумывать.

P0 для следующего захода:

1. `TaskRelation` / универсальные связи задач: заказ, лид, обращение, отзыв, товар, клиент, поставщик, категория, объект биржи. Каждая страница сущности показывает связанные задачи.
2. Notification center v2: входящие/исходящие, роли, адресаты, каналы, quiet hours, повторы, статус доставки, связь с задачей/заказом/лидом.
3. ARAY phone UX: скрытая клавиатура/T9, история и архив чатов, сортировка, hover-subtitles над чатом, мягкие подсказки.
4. Универсальный slide/popup стандарт: все наши панели кроме самой капсулы открываются справа/снизу с одним эффектом листания.
5. Voice/mic settings: устройства, расписание, рабочий график ARAY, напоминание включить голос/микрофон, только с согласием пользователя.
6. Терминал/биржа: корзина и оформление как ПилоРус-попап, справа вместо корзины показывать аналитику/котировки, когда корзина скрыта.
7. Резиновая проверка desktop/tablet/mobile/touch/TV: ARAY, терминал, биржа, задачи, финансы, меню.

P1 зафиксировать, не потерять:

- live translator mode и передача разговора между пользователями;
- ARAY как внутренний мессенджер: может сообщить человеку, но после подтверждения;
- пуши и уведомления лучше мессенджера;
- задачи создаются правильного вида: задача, заказ, заявка, лид, обращение, отзыв и т.д.;
- генерация фото товаров, видео, логотипов, брендбуков, названия, домена, хостинга, сайта в один клик как будущий контур конструктора;
- маркетплейс/биржа: категории -> магазины/исполнители -> товары/услуги, плюс честная аналитика по каждой сущности.

Следующий отчёт Арману писать коротко и по-человечески: что сделал, где смотреть, что beta, какой следующий шаг.

## Рабочий протокол "скрин -> план -> агенты -> результат" от 06.05.2026

Арман может просто сказать раздел, показать скрин или описать ощущение. Новый агент не должен просить техническое ТЗ. Нужно самому:

1. Найти прошлую память: этот файл, live-checklist, roadmap, agency OS, design system, CLAUDE/memory.
2. Проверить текущий код раздела, API, связанные компоненты, роли, настройки, ARAY-сценарии и логи dev-сервера.
3. Посмотреть страницу как продукт: дизайн, функции, удобство, мобильная/планшетная/desktop версия, скорость, ошибки, лишние кнопки, дубли поиска/back/header.
4. Сформулировать профессиональный план и согласовать его с Арманом до крупной реализации.
5. Запустить агентов только на узкие непересекающиеся задачи: аудит, дизайн, API, mobile, performance, QA.
6. Главный Codex делает основной кусок, принимает агентов, проверяет diff, запускает TypeScript/quality, обновляет checklist и дает человеческий отчет.

Таймбокс одного прохода: 15-30 минут на понятный кусок. Если раздел большой, делить на несколько проходов, а не пытаться размазать все сразу.

Режим ускорения 1.5x от 06.05.2026: работаем быстрее и дороже по вычислениям, поэтому дедлайны сжимаются без снижения качества. Preflight/план - 3-5 минут, read-only агент - 4-7 минут, маленький patch-agent - 8-15 минут, сложный slice - 15-25 минут. Если агент не укладывается, Main Codex принимает уже готовое полезное, закрывает риск сам или дробит задачу дальше. Скорость не отменяет `npm run quality`, проверку логов и mobile/tablet/desktop smoke.

Закон детальной приемки от 06.05.2026: пока работа не проверена подробно, ее нельзя сдавать Арману как готовую. Минимум приемки: сценарий глазами в браузере, быстрые действия/запросы, mobile/tablet/desktop smoke по затронутому UI, TypeScript, `npm run quality`, логи сервера/браузера и честный список того, что осталось beta или не проверено. Если найден даже маленький пользовательский провал, как пустой результат по быстрому чипу, это не "готово", а P1-fix до отчета.

Закон continuity для новых чатов от 06.05.2026: новый чат не начинает с нуля и не просит Армана повторять договоренности. Перед работой нужно прочитать этот файл, live-checklist, roadmap, agency OS, design system и `CLAUDE.md`; считать их единой системой нашей работы: агентство, план, дедлайны, профессиональная рекомендация, уникальная ARAY-фича, детальная приемка и человеческий отчет.

Закон автоматизации новых разделов от 06.05.2026: каждый новый раздел или фича подключается к единым системам через центральные модели и реестры, а не через ручные дубли. Раздел добавляется один раз и сразу попадает в навигацию, поиск, ARAY-контекст, mobile/tablet/desktop smoke и quality-gates. Ручные повторы запрещены без явной причины; Codex молча автоматизирует повторяемые места, чтобы будущие разделы не требовали отдельных правок навигации/поиска.

Закон ARAY identity от 06.05.2026: ARAY AI, агенты, бюджет ARAY, контекстные действия, капсула и все навигационные поверхности используют единый `ArayOrb`/`ArayIcon` из `components/shared/aray-orb.tsx`. Случайные lucide-иконки для ARAY запрещены. Если иконка визуально перегружает место, лучше использовать спокойную текстовую ARAY-подпись, группировку или спросить Армана, а не ставить лишний значок.

Закон ARAY events от 06.05.2026: открытие ARAY, голосовой режим, закрытие и отправка умного prompt всегда идут через `components/store/aray-events.ts`. Нельзя разбрасывать по компонентам ручные `window.dispatchEvent("aray:open")`, потому что lazy-mount, pending prompt, голос и очистка навигационной капсулы должны работать одинаково на desktop/mobile/tablet и в новых разделах.

Закон Navigation OS v3 от 06.05.2026: карта админки живет в `components/admin/admin-navigation-registry.ts`, смысловые секции - в `components/admin/admin-nav-structure.ts`, контекст поиска/ARAY/quick links - в `components/admin/admin-navigation-model.ts`. Рабочий стол = `main`; продажи = терминал/заказы/доставка/клиенты/CRM/задачи; магазин = каталог/товары/категории/склад/медиа/импорт; ARAY = AI-центр/агенты/бюджет/лимиты; настройки = бизнес/сайт/оформление/терминалы/команда/здоровье; помощь = гайды/обучение. Настройки не живут в магазине, ARAY-настройки не живут в общих настройках. `npm run nav:check` обязан падать при дублях href, неправильной группе, ручных staff-списках account drawer или старых quick links.

Закон UI integrity от 06.05.2026: хороший визуальный baseline нельзя "улучшать" без сравнения до/после. Перед изменением капсулы, ORB, hover, модалки или навигационной панели нужно проверить действующий закон, сохранить смысл эталона и не менять геометрию без прямой причины. Левая navigation capsule остается высокой и стабильной, короткие группы не сжимают ее. ARAY ORB в rail держит размер `2.5rem` и не scale-ится на hover. Строки popup-навигации используют спокойный muted hover; neon/conic/edge-ring запрещены для `.admin-nav-panel-item`. Градиентный edge-hover Армана применяется только к карточкам и важным interactive surface, не к меню, кнопкам, формам и рядовым строкам.

Закон ARAY orb purity от 06.05.2026: маленький ARAY orb в rail не получает дополнительные текстовые бейджи (`AI`) и декоративные cue-чипы поверх сферы. На малом размере это выглядит как случайная заплатка и спорит с фирменным знаком. Смысл ARAY передается через сам orb, `aria-label/title` и контекст меню, а не через микротекст на логотипе. `scripts/validate-admin-ui-integrity.js` блокирует возврат `admin-rail-aray-cue`.

Закон AdminModal/emoji от 06.05.2026: новые админские диалоги делаются через `components/admin/admin-modal.tsx` или `ConfirmDialog`. Новые ручные `fixed inset-0` overlay, native `alert/confirm/prompt` и видимые emoji в admin UI запрещены. `npm run quality` запускает `scripts/validate-admin-ui-integrity.js`: он фиксирует baseline капсулы/ORB/hover, workflows modal, settings hub и не дает добавлять новые legacy-попапы. Старый legacy debt чистится отдельными проходами по allowlist, но новые места не добавляются.

Закон ARAY contextual content от 06.05.2026: ARAY-подсказки, чипы и быстрые карточки показываются только если они конкретные, привязаны к текущей странице или реальным данным. Универсальные заглушки `ARAY следующий шаг`, `Что срочно?`, `Оживить продажи`, `Проверить риски` и ссылки `/admin/aray?intent=...next-step` запрещены как UI-fillers. Если настоящего сигнала нет, лучше скрыть ARAY-совет/чип, чем показывать красивый, но пустой текст. `scripts/validate-admin-ui-integrity.js` обязан ловить такие возвраты.

Закон balanced depth от 06.05.2026: тень в ARAY/админке является подсказкой слоя, а не декоративным пятном. В светлой теме нельзя использовать тяжёлые blur/shadow вокруг rail, navigation drawer, ARAY dock/panel и bottom sheets; сначала использовать border, тонкую заливку и малый inset, затем только мягкую тень с низкой opacity. Тень не должна быть заметнее текста, иконки или структуры. `scripts/validate-admin-ui-integrity.js` блокирует возврат старых тяжёлых shadow-значений для навигации и ARAY.

Закон safe build / Prisma DLL от 06.05.2026: на Windows локальный `next start` может держать Prisma query engine DLL и ломать `prisma generate` через `EPERM`. Нельзя тратить на это время вручную. `npm run build` и `npm run build:ci` обязаны идти через `scripts/next-build-safe.js`: скрипт сам находит Next-процессы этого проекта, останавливает их перед сборкой, запускает raw-build и возвращает локальный сервер на прежний порт. Если нужен чистый CI без рестарта, использовать `CI=1` или `--no-restart`. `scripts/validate-admin-ui-integrity.js` проверяет, что эта автоматика не удалена.

Урок 06.05.2026: если Арман показывает скрин и говорит "было красиво", Codex сначала возвращает эталон, потом автоматизирует защиту, потом только предлагает улучшения. Нельзя ломать то, что уже понравилось, ради абстрактного "улучшения".

В каждом плане обязательно есть:

- рекомендация Codex как профессионала: что лучше для UX, скорости, бизнеса, поддержки и качества;
- уникальная фича для ARAY/ПилоРус: не копировать обычные CRM, а добавлять наш фирменный смысл, если он безопасен и полезен.
- полный контур: архитектура, закон раздела, дизайн, функции, оптимизация, автоматизация/ARAY, выполнение агентами, тесты, проверка логов/устройств и показ результата Арману.
- агентское управление: каждому агенту задается владение, дедлайн, результат и критерий приемки; Main Codex принимает работу, а не пересылает Арману сырые выводы.

- при новом принципе дизайна - `DESIGN_SYSTEM.md`;
- при новом законе работы - `CLAUDE.md` или этот файл.

Статусы:

- `TODO` - еще не трогали;
- `DESIGNED` - архитектура/контракт зафиксированы, код еще не подключен;
- `IN_PROGRESS` - сейчас в работе;
- `BETA` - можно пользоваться, но есть честно отмеченные ограничения;
- `READY_LOCAL` - локально готово, проверки прошли;
- `NEEDS_REVIEW` - нужен взгляд Армана;
- `DEPLOY_READY` - можно деплоить после команды;
- `DONE` - проверено, закреплено, в checklist закрыто;
- `BLOCKED` - нужен ключ, API, юридическое решение или внешний доступ.

## Ежедневный ритм

Создана automation `aray-daily-admin-checklist`: каждый день в 10:00 она читает roadmap/checklist и готовит стартовый отчет дня. Если automation недоступна в новом окружении, вручную выполнить те же шаги из этого файла.

Создана automation `aray-admin-workday-pulse`: каждые 4 часа она поднимает checklist и готовит короткий отчет по статусам, рискам и следующим агентским подзадачам. Она не редактирует код и не деплоит сама.

Формула дня:

1. Выбрать один главный раздел дня из `docs/aray-admin-live-checklist-2026-05-02.md`.
2. Пройти раздел по кругу: дизайн -> mobile -> автоматизация -> beta/ready статусы -> Arai/help -> проверки.
3. Агентам отдать параллельные узкие задачи, но с непересекающимися файлами.
4. Main Codex принимает работу агентов, проверяет код, запускает quality-gate.
5. Только после этого показывает Арману короткий отчет и просит посмотреть уже готовый результат.

## Формат отчета Арману

Отчет пишется человеческим языком, без технической каши.

Обязательный формат:

```text
Брат, отчет по разделу: <название>.

Где смотреть:
- <локальная ссылка или путь>: что именно проверить глазами.

Что сделал:
- простыми словами, без внутренних терминов.

Что теперь работает:
- конкретные сценарии пользователя.

Что помечено beta / что еще честно не готово:
- только реальные ограничения.

Проверки:
- TypeScript / quality / mobile / что не удалось проверить.

Следующий шаг:
- один понятный следующий раздел или действие.
```

Если было много требований Армана, отчет должен явно повторить ключевые пункты: "я не потерял: акции, продвижение, отзывы, рассылки, настройки, база знаний..." и указать, что они внесены в roadmap/checklist.

## Закон агентской работы

Агенты не заменяют финальную ответственность Codex. Они помогают быстро читать, чинить и проверять отдельные части.

Подробная модель "как веб-агентство" хранится в `docs/aray-production-agency-os-2026-05-02.md`.

Правила:

- перед запуском агента в сообщении указать его владение: раздел, файлы, что можно менять, что нельзя;
- один агент = один узкий результат;
- не давать двум агентам один и тот же write-set;
- агент обязан в финале указать: что сделал, какие файлы тронул, что проверить;
- Main Codex после агента обязан просмотреть изменения, не принимать вслепую;
- если агент закончил, checklist обновляет Main Codex;
- Арман видит не сырую работу агентов, а принятый результат, проверку и короткий отчет.

Шаблон управления:

1. `Agent Terminal`: терминал, заказы, касса, CRM sync.
2. `Agent Design`: модалки, alerts, typography, mobile, navigation.
3. `Agent Business`: товары, категории, склад, импорт, медиа.
4. `Agent Marketing`: продвижение, акции, отзывы, рассылки, аналитика.
5. `Agent Arai/Finance`: Arai chat, база знаний, финансы, ARC.
6. `Main Codex`: интеграция, проверки, roadmap, финальное качество, отчет Арману.

## Главный приоритет ближайших дней

1. Не потерять дорожную карту.
2. Довести терминал, заказы, CRM-синхронизацию и общую дизайн-систему до рабочего эталона.
3. Разложить настройки по мегаразделам, чтобы не было свалки.
4. Сделать "Управление бизнесом" ядром каталога, склада, медиа и настроек сайта.
5. Подготовить маркетинг: продвижение, акции, отзывы, рассылки.
6. Подготовить базу знаний и Арая, чтобы человек мог сам понять и настроить систему.
7. После этого идти к сайту Стройматериалов и конструктору.
